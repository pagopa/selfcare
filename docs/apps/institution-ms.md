# institution-ms

> Spring Boot microservice (historically "ms-core") that owns institutions, their onboarded products, delegations between institutions and PEC mail notifications.

| | |
|---|---|
| Path | `apps/institution-ms` |
| Stack | Spring Boot 3.3.0 via `selc-starter-parent` (app POM references `0.3.2-SNAPSHOT`), Java 17, blocking (Spring MVC + Spring Data MongoDB, OpenFeign clients) |
| Type | REST microservice |
| Tenants | Both: separate `-ar` and `-pnpg` deployments, tenant-aware data and storage layer |
| Infra | `infra/resources/institution-ms/` |

## Responsibilities

- Institution registry (`Institution` collection): create from IPA, ANAC, IVASS, Infocamere, PDA or raw data (one `CreateInstitutionStrategy*` per source), update, search, onboarded products, geotaxonomies, billing data.
- Onboarding bookkeeping on institutions (add/delete onboarded product, `HEAD /onboarding*` checks); on onboarding it upserts a `MailNotification` document consumed by [institution-send-mail-scheduler](institution-send-mail-scheduler.md).
- Delegations between institutions (`Delegations` collection): create, list (v1 and paginated v2), count, delete; notification e-mails to the delegate (SMTP/PEC and OneMail).
- Resend `sc-delegations` events from a date (`POST /events/delegations`). The normal event flow is done by [delegation-cdc](delegation-cdc.md); institution changes are published by [institution-cdc](institution-cdc.md).

| Resource | Usage |
|---|---|
| MongoDB `selcMsCore`: `Institution`, `Delegations`, `MailNotification` | Read/write; all three carry an internal `tenantId` |
| Event Hub `sc-delegations` | Resend of delegation events only (`EventsServiceImpl`) |

| SMTP (Aruba PEC) / OneMail | Delegation notifications to institutions / users |

## Multitenancy

- **Tenant resolution**: `X-Tenant-Id` is read by the `selc-commons-web` JWT filter (duplicated or missing headers are rejected), the JWT is verified with that tenant's key and the tenant is stored in `TenantContext`; `TenantJwtConfigurationValidator` fails startup if a supported tenant has no JWT key. The header is logged (`LogFilter`) and forwarded to Feign clients (`TenantHeaderInterceptor`).
- **Resource selection**: MongoDB connection/database, JWT key and the `products` / `mail-templates` blob bindings come from `SELFCARE_TENANT_DATA_ISOLATION` (`TenantProductCatalogService` loads one product catalogue per tenant). Each Terraform stack registers only its own tenant (`AR` or `PNPG`).
- **Data isolation**: `TenantOwnershipPolicy` adds the `tenantId` criterion to queries (including aggregation joins), `TenantAwareEntityWriter` stamps `tenantId` on writes and rejects ownership conflicts. All six stacks currently set `TENANT_STRICT_DATA_ISOLATION=false` (compatibility mode: untagged legacy documents are still visible); the code default is `true`.
- **Readiness**: `mongoReadiness` pings the database of every supported tenant.

### OpenSpec change: `institution-ms-multitenant-database-layer`

Spec-driven change stored in `apps/institution-ms/openspec/` (not archived yet; all tasks marked done):

- [Proposal](../../apps/institution-ms/openspec/changes/institution-ms-multitenant-database-layer/proposal.md): adopt the `user-group-ms` model (shared tenant resolution, registry-based Mongo routing, persisted `tenantId`, scoped queries) for `Institution`, `Delegations` and `MailNotification`; strict mode is breaking for untagged data, so backfill or a compatibility window is needed.
- [Design](../../apps/institution-ms/openspec/changes/institution-ms-multitenant-database-layer/design.md): reuse the commons tenancy graph, keep the custom Mongo converter, centralize ownership predicates at the DAO boundary, scope aggregation roots and joins separately, tenant-complete readiness, Terraform wiring and migration plan.
- [Tasks](../../apps/institution-ms/openspec/changes/institution-ms-multitenant-database-layer/tasks.md): 8 groups (shared integration, ownership policy, institution, delegation, mail notification, readiness, acceptance tests, Terraform).
- [Spec delta `institution-tenant-persistence`](../../apps/institution-ms/openspec/changes/institution-ms-multitenant-database-layer/specs/institution-tenant-persistence/spec.md): requirements and scenarios for tenant scope, registry bindings, startup validation, ownership, query/aggregation isolation, legacy compatibility and readiness.

The proposal lists tenant-aware Azure Storage as out of scope; the current code and Terraform nevertheless already route product and mail-template storage through the tenant registry (README section "Tenant-aware blob storage").

## Build, run and test

```bash
mvn -f apps/institution-ms/pom.xml clean package
mvn -f apps/institution-ms/pom.xml test
cd apps/institution-ms && mvn spring-boot:run -pl app
# regenerate app/src/main/docs/openapi.json
cd apps/institution-ms && mvn test -pl app -am -Dtest=SwaggerConfigTest -Dsurefire.failIfNoSpecifiedTests=false
# Cucumber integration tests (Docker required), as in CI: run from apps/institution-ms
mvn test -Dtest=it.pagopa.selfcare.mscore.integration_test.CucumberSuite -Dsurefire.failIfNoSpecifiedTests=false
mvn --projects :test-coverage --also-make verify -Pinstitution-ms,report
```

Cucumber features in `app/src/test/resources/features/` (institution, delegation, delegationV2, onboarding, external, management, tenant-isolation). The runner starts `apps/institution-ms/docker-compose.yml` (MongoDB, Azurite, Azure CLI, MockServer, a `userms` container).

## Deployment

- Container Apps `selc-<env>-institution-ms` (AR) and `selc-<env>-pnpg-institution-ms` (PNPG), image `selfcare-institution-ms`, stacks `dev|uat|prod-ar` and `dev|uat|prod-pnpg`; the stacks also provision database `selcMsCore` and collections `Institution`, `Delegations`, `MailNotification`.
- PR: `.github/workflows/pr_institution_ms.yml`, `.github/workflows/pr_institution_ms_infra.yml`; integration tests: `.github/workflows/integration_test_institution_ms.yml`.
- Release: `.github/workflows/trigger_release_institution_ms.yml` → `release_app.yml` for `ar` and `pnpg`; DEV auto-release via `trigger_deploy_after_merge.yml`.
